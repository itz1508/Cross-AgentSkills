# OneShot — tracing and continuity questions for later use

**Summary:** A source-grounded question bank for evaluating knowledge tracing without changing OneShot Runtime ownership or inventing execution evidence.

Date: 2026-11-08 (America/Los_Angeles)
Status: OPEN QUESTIONS ONLY — not an approved implementation plan or acceptance record.

## A. Decide the actual problem first

1. What specific history is being lost: chat text, requirements, decisions, code changes, failed attempts, or verification evidence?
2. Which records already exist in OneShot's Git repository, task/event stores, `search.log`, `audit.log`, `plan.log`, `build.log`, and approved `mem.log`?
3. Which information is missing from those authoritative records, rather than merely difficult to retrieve?
4. Are we searching knowledge across sessions, tracing an individual execution, or attempting both? Which subsystem owns each?
5. Can an existing search/index feature solve the problem without adding an Obsidian vault?

## B. Session provenance — `session-search`

6. Given a requirement or file name, can we recover the exact originating session ID, message, timestamp, and source?
7. Does the tool differentiate between a search match, an available complete transcript, and a history-only entry whose transcript was deleted?
8. How do we know its session graph is current, and what happens if it is stale or unavailable?
9. Can search retrieve a bounded relevant excerpt instead of exposing an entire conversation log?
10. Can a known fixture query retrieve the correct prior decision without confusing similarly named projects?

## C. Cross-agent knowledge origin — `memory-bridge`

11. What provenance fields exist today for each reusable lesson, and which agent/tool originally produced it?
12. Is a lesson supported by original evidence or only by another agent's previous summary?
13. Can we compare knowledge generated by different tools without treating agreement as independent verification?
14. If the manifest or source is missing, does retrieval say **unknown** rather than inventing origin?
15. Which observations belong in a searchable knowledge record, and which must stay in authoritative execution logs?

## D. Relationships — `cross-linker`

16. Can we link a decision to its source, revision, affected files, plan, and verification receipt with exact identifiers?
17. Which relationships are observed and which are merely inferred from shared tags or similar language?
18. How will inferred links avoid becoming evidence or authority for build admission?
19. Can we detect duplicate lessons, contradictions, superseded decisions, and orphaned references before adding links?
20. How do we prevent the same lesson being recreated under multiple projects or agent names?

## E. Recovery — `wiki-rebuild`

21. Do we actually have an Obsidian vault whose current knowledge must be rebuilt, or are we only trying to recover missing chat history?
22. Is the smallest safe action an archive, incremental update, deduplication, or full rebuild?
23. Can an archive be verified, restored to a temporary location, and compared with the original before any live content is cleared?
24. Does the re-ingest path preserve original source provenance and distinguish deleted/unrecoverable transcripts?
25. What is the explicit recovery/rollback procedure if re-ingestion is interrupted?

## F. OneShot admission and evidence boundaries

26. Could any wiki summary, generated link, or caller-provided `verified` string accidentally be interpreted as a Runtime approval or verification receipt?
27. Can trace records bind to exact task/run/revision/source identities without altering existing stage contracts?
28. Who can read, index, edit, or delete conversation and code evidence? What data retention limits apply?
29. Which deterministic tests establish correct retrieval, provenance, deduplication, stale-source handling, and denial of invented results?
30. After a controlled evaluation, what measured improvement justifies retaining the skill instead of using existing records and search tools?

## Suggested evaluation prompt for the future

> Evaluate the extracted Obsidian Wiki tracing candidates against OneShot's actual existing sources. Inspect the repository and `/OneShot/bootstrap/START_HERE.md` first. Identify what the current logs, Git history, stores, and memory records already support. For each candidate, classify: applicable, redundant, missing prerequisite, or out of scope. Use labeled fixtures with known originating sessions, source identities, and contradicted/superseded decisions. Keep the assessment read-only. Do not install or run wiki-rebuild, create an alternative Runtime, or grant authority to wiki-derived evidence. Report observed retrieval correctness, provenance coverage, missing sources, and next decisions; do not claim production E2E without executing it.
